## How to use this file

There are **two repos**: `axlint` (the product) and `trackr` (the demo target, deployed on Railway). Put this file and the spec in the `axlint` repo as `docs/STORIES.md` and `docs/SPEC.md`; S2 runs in the `trackr` repo, everything else in `axlint`. Run stories in order. For each code story, start a fresh coding-agent session and paste:

> Implement story **S#** from `docs/STORIES.md`. The full spec is in `docs/SPEC.md`; follow it exactly and don't add anything the story doesn't ask for. Stop when every acceptance check passes, and tell me which ones you ran.

A story is done only when its checks pass. Items marked **(you)** need a person.

**What `trackr` is:** the bug tracker for a fictional online store, Larkspur Goods: 40 issues from a four-person team, exposed through three read-only MCP tools with realistically vague descriptions. AX Lint audits and fixes it live. It's ours so the demo is repeatable.

**If code isn't allowed before Saturday:** do S1 as normal, S2–S4 on paper and as account setup, and run S5 first thing Saturday before S6.

**Repo layout** (TypeScript):

- `trackr` repo: `src/tools.ts`, `src/validation.ts`, `src/handlers.ts`, `fixtures/`, `scripts/gen-fixtures.ts`, `scripts/fidelity.test.ts`, tests, and a short README describing Larkspur Goods.

Unit tests that need `trackr`'s source use a copy of its `src/tools.ts` pinned to a commit, kept in `test/fixtures/`.

## S2 · Build `trackr` (in the `trackr` repo)

The target server and its data, per the spec section "The target: `trackr`". Fixture issues should read like a real small e-commerce team's tracker: titles, bodies and comment threads about checkout, login, search, the cart, payments and emails, in a consistent voice per person.

- TypeScript MCP server on mcp-use over streamable HTTP. Three read-only tools with the **baseline descriptions verbatim** and no `.describe()` on parameters.
- `src/tools.ts` follows the spec's layout exactly; `src/validation.ts` exports `STATUS_VALUES` and the handler enforces it; the schema stays `z.string()`; handler logic only in `src/handlers.ts`.
- `serverInfo.version` reports `<DEPLOYMENT_ID>@<GIT_SHA>` from environment variables.
- Deployed on Railway from its GitHub repo with auto-deploy on push. `DEPLOYMENT_ID` is a fixed service variable; the SHA comes from the commit-SHA variable Railway injects (confirm the name). Data is fake and read-only, so a public URL is fine.
- `fixtures/issues.json` generated by a seeded script, matching every count in the spec.

**Acceptance:**
- [ ] `tools/list` descriptions match the spec byte for byte.
- [ ] Unit tests cover every runtime behavior in the spec table, including `Invalid status` and `Issue not found`.
- [ ] A test asserts every fixture count; Maria's open issues are at least 5,000 tokens with comments and under 500 without.
- [ ] On the Railway URL, `serverInfo.version` shows the deployment ID and current commit SHA, and a new push changes the SHA.
- [ ] Push-to-live redeploy time measured and noted for the demo script.

## S3 · Prove the demo works, and the real-server gate

Three scripts that answer the riskiest questions before any AX Lint code exists, including whether a real server can replace `trackr` as the demo target.

- `scripts/hand-run.ts` (in `axlint`, pointed at `trackr`'s Railway URL): runs the spec's four tasks, 3 times each, against the baseline and a hand-applied version of the compact patch, with the spec's system prompt, the temperature parameter omitted for Sonnet 5.5, single turn. Prints chosen tool, arguments, pass/fail and result tokens for all 24 trials.
- `scripts/fidelity.test.ts` (in `trackr`, taking a patch file as input): applies the compact patch's source edits to a copy of `trackr`, starts it, and asserts `tools/list` descriptions equal the patch values exactly. Record what mcp-use emits for a `.describe()` on an optional parameter.

- **Real-server benchmark** (`scripts/hand-run-memory.ts`): the official MCP Knowledge Graph Memory reference server, cloned at pinned commit `bbb701e`, run locally over stdio with a seeded fictional graph large enough that `read_graph` is expensive. Baseline versus a hand-written compact patch to the three read-tool descriptions. Rules:
  - **The model sees all nine tools**, so the routing problem is realistic.
  - **Only read tools execute.** `read_graph`, `search_nodes` and `open_nodes` are on an allowlist enforced in the code that executes calls. A write tool chosen by the model is scored `wrong_tool` and never run.
  - **One fresh server process per trial:** copy the seed graph to a temp directory, start the pinned server over stdio with `MEMORY_FILE_PATH` pointing there, run the trial, stop the process, delete the temp files. Trials may run concurrently, each with its own process and file.
  - Four tasks, 3 trials each:

  | Task | Prompt | Scored as |
  | --- | --- | --- |
  | Broad retrieval | "Show me everything you remember about this project." | Pass if `read_graph` |
  | Search | "Find anything mentioning the checkout migration." | Pass if `search_nodes` with a relevant query |
  | Exact retrieval (control) | "Open the memory entries for Priya Nair and Dev Patel." | Pass if `open_nodes` with both names |
  | Boundary | "What do you know about Priya Nair's work on the checkout migration?" | **Not scored.** Record which tool is chosen and the result tokens |

  Also record result tokens for every trial, since `read_graph` on a narrow question is the most likely real failure.

**Acceptance:**
- [ ] All three scripts run.
- [ ] **(you)** `trackr` results compared to the spec's hypotheses; any failed hypothesis handled with the spec's rules and recorded. Don't change prompts to make the baseline fail.
- [ ] **(you)** The real-server gate, decided from the memory results:

  | Outcome | Decision |
  | --- | --- |
  | Baseline fails at least two meaningful scored tasks, candidate improves them, control holds | Memory server is the primary demo |
  | Baseline fails only one task, but the improvement is substantial | Memory server only if the demo is still compelling |
  | Baseline passes almost everything | `trackr` stays primary |
  | Hand-applying the patch to `src/memory/index.ts` doesn't reproduce the verified metadata | `trackr` stays primary; don't expand source patching during the hackathon |
  | The benchmark needed substantial new infrastructure | `trackr` stays primary, for reliability |

  **If the memory server wins**, update the spec once:
  - The target becomes repo + pinned commit + start command, run inside the Blaxel sandbox over stdio, one fresh process per trial. Railway isn't needed, and `confirm_patch` checks out the patched commit itself, so revision identity is the commit.
  - Source edits go through a narrow adapter interface, `supports(source)` and `generateEdits(source, ops)`, with one adapter for the memory server's `registerTool` pattern. `trackr` keeps its own adapter as the fallback. The verification engine never depends on source layout.
  - On stage, describe it as "the official MCP Memory reference server," and frame the finding as a behavior problem source tests can't catch: the tools work correctly, but agents sometimes read the whole graph when a targeted search would do.

  **If `trackr` wins**, the spec stays as is, and the memory server becomes a read-only audit in `examples/`.
- [ ] The fidelity test passes; if not, change the prescribed edit pattern until it does and update the spec.

## S5 · Core library

All pure functions in `axlint/src/core/`, no network or model calls, all unit-tested.

- **Contracts:** Zod schemas for every contract in the spec, including all seven run statuses. `WireOp` allows only the two description ops.
- **Scoring:** the five matchers; `scoreTrial` returning `passed`, `failure` and `checks`; `explain` producing the deterministic explanation text.
- **Tools JSON:** `canonicalize` (sorts keys and tools, never drops fields), `hashTools`, `applyWireOps`, and `diffTools` with JSON paths.
- **Source edits:** the spec's two generator rules for `trackr`'s layout, failing with `unsupported_layout` unless each target matches exactly once; returns edits, unified diff and `base_source_hashes`.
- **Verdict:** the spec's rules in order: Regressed, then Inconclusive for any `insufficient_data`, then Improved, then Inconclusive.
- **Audit checks:** every finding kind, including the deterministic overlap rule.

**Acceptance:**
- [ ] Every JSON example in the spec parses with its schema.
- [ ] The `t1-route` baseline example reproduces exactly, explanation included.
- [ ] Applying wire ops changes only `description` fields; `diffTools` reports `additionalProperties` and `required` differences.
- [ ] Generated source edits pass S3's fidelity test.
- [ ] Verdict tests include: control with insufficient data plus big gains elsewhere is Inconclusive; one-task drop of 1 is Inconclusive; observed control regression is Regressed.
- [ ] On baseline `trackr`, audit returns F1–F3 and no overlap finding for `get_issue`; on the patched list, F1 is gone.

## S6 · Verification runner and run tools

- **`runner/`:** the spec's verification procedure, steps 1–10, using the core library. Reads its input from a file, writes `progress.json` after every trial and `result.json` at the end, including the exact `candidate_tools` and `server_version`. Get it working locally first, then inside Blaxel using the S4 pattern.
- **`verify_patch`:** validates input, starts the sandbox and runner, returns `run_id` in under a second.
- **`get_verification_result`:** reads the sandbox files and maps every case to one of the seven statuses. AX Lint stores nothing.

**Acceptance:**
- [ ] From an MCP client: start a run on `trackr`, poll to `complete`, receive all 24 trials in a result that validates against the schema.
- [ ] A stale `base_tools_hash` produces `failed` with `stale_patch`.
- [ ] A made-up run ID returns `run_expired` or `run_unavailable`; restarting AX Lint mid-run loses nothing.

## S7 · `audit_server`, `propose_patch`, `confirm_patch`

- **`audit_server`:** reads `tools/list` and `serverInfo.version`, runs the audit checks, counts static tool tokens. Never calls a tool on the target.
- **`propose_patch`:** one model call for `wire_ops` (structured output, one retry on validation failure), then validation, source edits, candidate and hashes from the core library. `compact` and `full` styles as the spec defines.
- **`confirm_patch`:** the four gates in order, each with its named error.

**Acceptance:**
- [ ] Audit on `trackr` returns F1–F3 with `server_version`.
- [ ] A `compact` patch on `trackr` addresses F1–F3 with description ops only and passes the fidelity test; an op naming a nonexistent parameter is rejected.
- [ ] `confirm_patch` fails at gate 1 for an Inconclusive run, at gate 3 before redeploying, and passes after a real apply and redeploy.

## S9 · Polish (only after S8)

In this order; stop wherever the clock runs out.

1. **Presentation viewer** (about 3 hours). A read-only page served by AX Lint at `/runs/<run_id>`, shown next to the terminal during the demo. It never controls anything; Claude Code still drives the loop. It polls the same run files `get_verification_result` reads and shows, in order:
   - **Audit:** the server's tools as cards, with findings as badges.
   - **Patch:** old versus new description, word-level diff.
   - **Trials, live:** a grid of tasks × trials × before/after, each cell filling in red or green with the chosen tool as trials complete.
   - **The story trial:** one representative before/after pair with the chosen tools, result tokens, and the deterministic explanation.
   - **Verdict:** Improved, Inconclusive or Regressed, with pass counts, token comparison and the provisional label.
   - **Confirm:** the four gates ticking off.

   A **replay mode** (`?replay=<recorded run>`) plays a recorded run's files back at real speed. It's for rehearsal and is the fallback if the live run fails.

   Acceptance:
   - [ ] Opening the page mid-run shows trials appearing as they finish, with no page reload.
   - [ ] Replay of a recorded run looks identical to the live view.
   - [ ] Readable from the back of a room: large type, high contrast, nothing below 16px.
   - [ ] Stretch, only if time remains: the same view returned as an MCP App from `get_verification_result`, for clients that render MCP Apps.

2. Read-only audits of the official Knowledge Graph Memory server and the study's `yfinance` server, saved to `examples/`.
3. `README.md`: one-line description, how to mount AX Lint, the five tools, the apply procedure (check `base_source_hashes` before applying), the generality statement, the provisional-results label, links to the spec and the study.
4. The `full`-style second patch on the demo target, verified; compact and full results saved to `examples/`.
5. Eval-action exporter, **only if (you)** a hand-written case already runs through `mcp-use/eval-action` on `trackr` by 9:30 PM. Otherwise skip and list it in the README roadmap.

**Acceptance:**
- [ ] Neither public audit called a tool on the public server.
- [ ] README states the source-edit generator supports one layout.
